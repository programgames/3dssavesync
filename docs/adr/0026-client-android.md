# Android client: same repository, Kotlin port with shared fixtures, SAF only, minSdk 24

An Android phone runs DS, GB, GBC, GBA and 3DS emulators. It becomes a third kind of Client, next to the 3DS app and the PC program.

## Decision

- **One repository, several clients.** The app lives in `android/`, next to `3ds/`, `client/` and `server/`. One pull request can change the protocol, the server and every client together, and the CI checks them together.
- **The sync logic is ported to Kotlin**, not shared as a library. The rules are small (`etat`, SRAM rules, Keys), and Go on Android (gomobile) would add a native build, a JNI layer and a larger APK for a few hundred lines. To keep the three ports equal, the Kotlin JVM tests read the same files as the others, in place: `tests/cas_etat.csv` (3-way State) and `tests/saves.json` (server list). They also run the Sync against the real `server/server.py` on 127.0.0.1, like `client/launcher_test.go`.
- **Same protocol as the PC**: `Authorization: Bearer`, `GET /saves`, conditional `PUT` (`If-Match` / `If-None-Match: *`, a `412` starts a new pass), `X-Client: android`, `PUT /saves/<key>/name` (ADR 0018). The address keeps its own scheme: plain HTTP for a home server, HTTPS the same way.
- **Storage Access Framework only.** The user picks each ROM folder and save folder with the system folder picker (`ACTION_OPEN_DOCUMENT_TREE`, persisted read and write grants). No "All files access" permission: SAF gives the same reach for the supported emulators, and Android/data stays closed to both (see the [Android guide](../guide-android.md#emulators)). The app never writes outside a chosen folder and never deletes a file it did not create. One exception, like the PC (`client/sync.go` download): when the first save of a 3DS game never started in Azahar fails midway, the app removes the folder, `.metadata` and `main` it has just created in that same operation, so that Azahar sees a game never started instead of a broken save; nothing that existed before is touched. Backup copies go to the app's own folder (`getExternalFilesDir`), visible over USB, named like the PC (`<emulator>/<name>-<date>.<ext>`). Bases stay in app-private storage, one JSON file per emulator entry.
- **RetroArch: one saves folder, the app finds each save.** The user chooses a ROM folder per system and, once, `RetroArch/saves`. The scan looks for the save in the folder of the chosen core, at the root of the saves folder, then next to the ROM, and takes the newest when several exist (the one RetroArch writes now after a settings change); never the folder of another core. One folder per core per system meant up to six picks, and the most frequent mistake (`saves` instead of `saves/mGBA`) showed as a list full of To download.
- **Installed emulators first, through `<queries>`.** The manifest lists the packages of the known emulators (`Profiles.kt`, checked by `ProfilesTest`), so Android 11+ lets the app see if they are installed. No `QUERY_ALL_PACKAGES`: the app needs to know about these apps only.
- **Replacing a save without an atomic rename.** SAF has no rename that replaces a file, and a provider may not even honour truncation (`"w"` can leave old trailing bytes). So the app: (1) writes a Backup copy in its own folder, reads it back and compares it; (2) opens the save with `"wt"` (truncate), writes the new content and syncs it to the disk; (3) reads it back and compares. On a mismatch it writes the old content back and checks it again; if that fails too, it stops and names the Backup copy. A verified copy outside the folder exists before the file is touched, so no failure can lose the old save.
- **minSdk 24 (Android 7.0), compile and target 36.** 24 is the floor of the next Compose and WorkManager versions and of the network security config (cleartext opt-in), and every supported emulator needs Android 7 or later anyway. Target 36 is what Google Play asks since August 2026 (the APK is on GitHub only, but the same rules keep it ready); it forces edge-to-edge and predictive back, which the app already uses (`BackHandler`). Not 37 yet: target 37 blocks the home network without the `ACCESS_LOCAL_NETWORK` permission, which needs its own request flow first. The AndroidX versions are the last ones that build with compileSdk 36 (Compose BOM 2026.06, core 1.18); Robolectric runs the UI tests on Android 16, which needs Java 21 for the tests only.

## Save safety rules

A save can hold hundreds of hours of play. The app never replaces or uploads a save on a guess: when a case is not clear, it shows a Conflict and the user chooses. The phones differ (Android 7 to 16, many makers, SD cards), so the rules use only the files and the app's own records, never a property of one device.

- **Came back.** An emulator left open in the recent apps keeps the old save in memory and can write it back after a Download. The 3-way State then says To upload, and the background upload would send the old progress to every device. So each Download keeps, next to the Base, the Hash of the Local save it replaced (`bases/replaced/<emulator>.json`). When the Local save is that Hash again and the server still has the downloaded version (the Base), the game is a Conflict with the reason "This save came back to the version that was replaced: the emulator was probably still open". `state()` stays the shared rule; the check is in `Syncer` (`status`, `sync`, `uploadOnly`). An Upload of the game ends the rule; an In sync pass does not, because the emulator can write later.
- **Emulator changes.** A Base is only true for the files it was made with. A change of folder, core, extension, system or "Saves next to the ROMs" forgets the Bases of that emulator entry, and its came-back Hashes. Without a Base, a save that the server also has is In sync or a Conflict: never To upload because of an old record. The deletion runs on the app's single io thread, so a sync in progress cannot write a Base after it. Removing an entry deletes its Bases too. A new name keeps them.
- **Interrupted write.** `"wt"` truncates the file before the new content is written, so a kill in between leaves a cut save. Before it writes, `replace` stores a marker in app-private storage (`pending.json`: Key and file, path of the Backup copy, Hash of the new content), and removes it after the read-back. A marker left at the next scan, with a file that does not have that Hash, means the write did not finish: the game is **Interrupted**, a Conflict with two choices only, "Use the server save" (the usual verified Download) or "Restore the backup copy" (the copy goes back through `replace`, with a copy of the cut file first). The cut file is never uploaded and never kept as it is. The marker belongs to the file, not to the emulator entry, so a folder change does not forget it; it keeps the first Backup copy when a later write over the cut file fails too. A file that has the Hash of the marker was fully written: the marker goes.
- **Big libraries.** The list keeps only the Hash, size, blank flag and Pokémon play time of each Local save, never its content: a Sync reads the file again. The Keys read in the ROM headers are cached by document, size and date (`romkeys.json`), so a refresh or a background pass opens only the new or changed ROMs; a provider that gives no size or date is read every time, and a damaged cache is made again.
- **Updates without uninstalling.** Uninstalling deletes the Backup copies, the Bases and the markers (`getExternalFilesDir`, `filesDir`). So the release APK is signed with one fixed key, kept as a CI secret, and its versionCode grows with each tag (major × 10000 + minor × 100 + patch). A new APK then installs over the old one. Without the secret, the CI builds no release APK and the release goes on without it; it never signs with a key of its own.

## Rejected options

- **A separate repository**: the fixtures, the protocol and the server would drift; a protocol change would need two pull requests in step.
- **gomobile (share `client/` Go code)**: native toolchain in the build, JNI glue, and the PC code reads files by path, not SAF documents.
- **`MANAGE_EXTERNAL_STORAGE`**: direct file paths, but it does not open other apps' `Android/data` folders either, and Play allows it only for a few app types.
- **Write to a temporary document, then rename**: `DocumentsContract.renameDocument` cannot replace an existing file, and some providers add " (1)" to the new name.
- **Detect a running emulator**: Android gives no way to see if another app runs or holds a file open. The 30-second check, the reminder and the "came back" rule work from the files only.
- **Keep the Bases after a folder change, or clear only the changed System**: the first is the stale-Base risk itself; the second needs a Key-to-System map for each profile, for a rare action whose only cost is a few Conflicts to confirm.

## Consequences

- A new rule in `etat` or in the SRAM rules is written three times (C, Go, Kotlin); the shared fixtures catch a port that differs.
- Aliases for ROM hacks (ADR 0014) are not ported yet: two ROMs with one Key are a Duplicate, never synced.
- The app syncs only when asked (no background sync) and does not start games; both can come later.
- Emulators that keep their saves in `Android/data` (Lemuroid, SkyEmu, Pizza Boy unless it can save elsewhere) cannot be synced. After each folder pick, the app says when a folder is in `Android/data` or holds no save, instead of a silent empty list.
